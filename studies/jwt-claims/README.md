# A masked JWT signature can still expose identity claims

At baseline `588e2d4`, a native signed JWT containing a synthetic customer ID,
name and email was partially masked. The header and signature became separate
surrogates; the entire base64url claims segment remained in outgoing SDK
requests. Encoding is reversible without the signing key. Restoring this text
correctly did not establish that the identity had been protected.

The corrected source recognizes supported compact JWT-shaped values and masks
each as **one SECRET value**, retaining the exact original in the vault. It
protects identity-bearing claims along with the rest of the credential.

| Controlled replay | Baseline | Corrected source |
| --- | ---: | ---: |
| Whole native tokens masked | 0/12 | 12/12 |
| Cases leaving encoded claims visible | 12/12 | 0/12 |
| Actual SDK requests with every example wholly masked | 0/12 | 12/12 |
| CLI/vault and CRLF restoration | 12/12 | 12/12 |
| Stream restoration, four chunk sizes | 48/48 | 48/48 |

[Before](results/before.json) and [after](results/after.json) retain actual masked
text and SDK request bodies, fixture hashes and source hashes. Every token and
identity in this study is synthetic. No token was issued by an identity service
or sent to a provider, and these figures are not production leak rates.

## Native fixtures and independent checks

[`cases.json`](cases.json) was generated by PyJWT 2.15.1 using HMAC (HS256,
HS384, HS512), RSA (RS256, PS256), EC (ES256) and Ed25519 (EdDSA). It also
covers an unsecured token, omitted `typ`, Unicode claims, a long claims set and
a header containing a key URL. Asymmetric private keys are discarded; only
verification public keys are retained. The HMAC key is explicitly synthetic.

The replay verifies signed fixtures through **PyJWT's signature verifier**,
independently of Veil's format recognizer, and compares decoded claims with
the constructed values. Time claims are not checked. The unsecured fixture is
decoded without signature verification and is labeled accordingly. The oracle
does not claim that a real issuer would accept these tokens.

This follows [RFC 7519 section 3](https://www.rfc-editor.org/rfc/rfc7519.html#section-3)
and [JWS compact serialization](https://www.rfc-editor.org/rfc/rfc7515.html#section-7.1).
JWT permits an unsecured `alg: "none"` form with an empty signature
([RFC 7519 section 6](https://www.rfc-editor.org/rfc/rfc7519.html#section-6));
its unencrypted claims still require privacy protection. PyJWT's
[algorithm documentation](https://pyjwt.readthedocs.io/en/stable/algorithms.html)
describes the independent encoder/verifier used here.

```sh
uv run python studies/jwt-claims/replay.py --oracle --sdk --require-fixed --output /tmp/jwt-after.json
uv run pytest tests/test_jwt_masking.py
```

The SDK replay uses the existing local echo HTTP transport and the real SDK
serializers: Chat Completions, Responses and Anthropic, each sync/async and
buffered/streaming. Each request contains seven representative native tokens.
The CLI separately creates a vault for each of the 12 cases, then checks exact
restoration of the original CRLF bytes. A bare package installation can replay
core/CLI without `--oracle` or `--sdk`; the library has no new runtime dependency.

To replay the baseline, export `588e2d4`, set `PYTHONPATH` to that archive's
`src/` and use the current driver without `--require-fixed`. Retained fixture
bytes are the reproducibility boundary. Regenerating with `generate.py` creates
fresh asymmetric signatures and public keys; it deliberately does not promise
identical bytes across generations.

## Recognition, precedence and limits

Veil decodes at most **16,384 encoded header characters** and requires a JSON
object with a nonempty string `alg`. `typ` is optional. Claims and signatures
stay opaque. An empty signature is recognized only with `alg: "none"`.
Compatible padded spellings are retained byte for byte; a regression constructs
the signed spelling with stdlib HMAC and verifies it independently with PyJWT.

This is **not an authentication validator**. Unknown algorithms and altered
signatures can still carry private claims, so recognition masks them without
executing a signature algorithm. Expiration, issuer/audience trust and claim validity
are outside this detector. Header key URLs are never fetched.

The enclosing token outranks a card-like signature fragment. A whole
credential-bearing URL can still enclose the token and win the overlap rule.
Repeated occurrences reuse one surrogate. Sentence punctuation stays outside
the token, including the distinction between an unsecured signature's final
dot and a following prose full stop.

Five-part JWE, detached/unencoded payloads, oversized or unreadable headers and
glued/multipart candidates are outside this recognizer's scope. It refuses a
shorter three-part prefix of a longer encoded value. Existing entropy scanning
still runs separately and does **not** establish complete coverage for rejected
candidates. In particular, this change is not a guarantee for every token-like
string or encoding. A Python header-parser recursion limit is handled without
crashing the scan.

The [technical-corpus receipt](results/corpus.json) confirms no changed resolved
detections across 1,483 retained files, 32,925,796 bytes, 2,616,034 words and
10,372 detections. Type, span, value, detector and confidence all match the
baseline. This checks collateral behavior on that corpus; it is not JWT recall
measurement in production.

`scaling.py` uses size parameters of 10,000, 100,000 and 1,000,000 for long
opaque claims, oversized headers, single words, many dots and repeated four-part
candidates. Encoded payloads and repeated-record inputs have different actual
byte counts, which are retained in the receipts. [Before](results/scaling-before.json) and
[after](results/scaling-after.json) retain input hashes, warmup/repeat counts and
timings for `SecretDetector.find`. They are controlled local measurements, not
end-to-end or worst-case latency guarantees.
